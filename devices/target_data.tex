\section{\scode{target_data} Construct}
\label{sec:target_data}

The \kcode{target_data} construct defines a region of code in which storage is
mapped to the device data environment of a target device. It can be used to map
storage to the device data environment for access in enclosed \kcode{target}
regions, thereby avoiding data-mapping overhead at each \kcode{target} region.
The \kcode{target_data} construct implicitly behaves as a composite construct
that includes the functionality of the \kcode{target_enter_data} and
\kcode{target_exit_data} directives for data-mapping on entry to and exit from
the region, respectively. The details of these composite semantics are described
in \specref{subsec:composite_target_data}.

Note that the directive name \kcode{target_data}, introduced in OpenMP 6.0, is
used in the text that describes the examples in this section, while the old
directive name \kcode{target data} continues to be used in code examples for
versions prior to OpenMP 6.0.

\subsection{Simple \scode{target_data} Construct}
\label{subsec:target_data_simple}
\index{constructs!target_data@\kcode{target_data}}
\index{target_data construct@\kcode{target_data} construct}

This example shows how the \kcode{target_data} construct maps storage to the
device data environment of a target device. Storage for the array sections
\ucode{v1[0:N]}, \ucode{v2[0:N]}, and \ucode{p[0:N]} is mapped to the device data
environment on entry to the \kcode{target_data} region. Inside the
\kcode{target_data} region, \ucode{v1}, \ucode{v2}, and \ucode{p} still refer to
the original storage of the array sections. However, inside the
\kcode{target} region that is enclosed in the \kcode{target_data} region the
variables refer to the storage of these array sections in the device data
environment. The variable \ucode{N}, being scalar, is by default treated as
firstprivate for the \kcode{target} construct, thereby getting its value from
the encountering task's data environment.

\subsection{\scode{target_data} Construct with \kcode{if} Clause}
\label{subsec:target_data_if}
\index{target data construct@\kcode{target data} construct!if clause@\kcode{if} clause}
\index{clauses!if@\kcode{if}}
\index{if clause@\kcode{if} clause}

The following example illustrates the use of the \kcode{if} clause on a
\kcode{target_data} construct and a nested \kcode{target} construct.  For both
constructs, the \kcode{if} clause sets the target device to the host device if
the condition evaluates to \vcode{false}. The condition, variable \ucode{N}
being smaller than a given threshold, is identical for both constructs, and so
their target devices are guaranteed to match. If the target device is a non-host
device, inside the \kcode{target} region the pointer variable \ucode{p} will
reference the storage for \ucode{p[0:N]} in its device data environment. If the
target device is the host device, then the \kcode{target} region executes on the
host device and \ucode{p} will reference the original storage for \ucode{p[0:N]}
in the enclosing host data environment.

If instead different \kcode{if} clause conditions were used for the constructs,
or if the clause only appeared on one of the constructs, then a target device
mismatch is possible that results in incorrect behavior. For instance, if the
condition evaluates to \vcode{false} for the \kcode{target_data} region only,
the \kcode{target} region will still execute on the non-host device but the
pointer variable \ucode{p} will reference the original storage for
\ucode{p[0:N]} in the enclosing host data environment that is potentially
inaccessible. If the condition evaluates to \vcode{false} for the \kcode{target}
region only, a different problem emerges. The \kcode{target_data} region may map
storage to and from a non-host device data environment, while the \kcode{target}
region operates only on storage in the host device data environment. At the end
of the \kcode{target_data} region, the array section \ucode{p[0:N]} will be
assigned from the device data environment to the original storage in the data
environment of the task that encountered the \kcode{target_data} construct,
resulting in undefined values in \ucode{p[0:N]}.

\subsection{\scode{target_data} as a Composite Directive}
\label{subsec:composite_target_data}
\index{target_data construct@\kcode{target_data} construct}
\index{constructs!target_data@\kcode{target_data}}

In the OpenMP Specification 6.0, new semantics were defined for the \kcode{target_data} construct that 
makes it a task-generating composite construct that has the effect of three task-generating 
constituent constructs when encountered: \kcode{target_enter_data}, \kcode{task}, and 
\kcode{target_exit_data}.
In the example below, the \kcode{target_data} construct is presented with its equivalent 
task-generating semantics for four different use cases.
In the four different cases, dependences on \ucode{t_} are used to enforce the ordering of 
the three tasks generated by the \kcode{target_data} construct.

In Case 1, a \kcode{target} construct with a \kcode{nowait} clause is executed within 
the \kcode{target_data} region. 
The semantically equivalent code is shown in Case 1E 
where the \kcode{target_enter_data} and \kcode{target_exit_data} directives produce 
the same mapping that is specified by the Case 1 \kcode{target_data} construct.
The task generated by the middle constituent construct, denoted by \ucode{T2} in Case 1E, 
is a transparent task and therefore allows dependences to be established between the 
\kcode{target} construct and the other two constituent constructs.
The structured block enclosed by the transparent task in Case 1E contains a \kcode{target} construct 
with the \kcode{nowait} clause, allowing the task \ucode{T2_1} to be deferred. 
Prior to OpenMP 6.0, the deferred task \ucode{T2_1} would outlive the \kcode{target_data} region;
in OpenMP 6.0, the implicit taskgroup ensures the completion of \ucode{T2_1} before
the end of the \kcode{target_data} region.
The \kcode{target_exit_data} construct is the final constituent construct of the \kcode{target_data} 
directive and is denoted by \ucode{T3} in Case 1E.  

In Case 2 the \kcode{nogroup} clause is used on the \kcode{target_data} directive.
Due to the effect of the \kcode{nogroup} clause in Case 2, the \kcode{target} region is not enclosed in 
a \kcode{taskgroup} in Case 2E. 
%Moreover, the \kcode{target} directive has to have a \kcode{nowait} in the equivalent code to ensure 
%that no additional synchronization is added. 
Prior to OpenMP 6.0, the behavior of Case 1 would be the same as Case 2, 
allowing the \kcode{target} construct with a \kcode{nowait} to start or continue after the completion of the 
\kcode{target_data} region.

In Case 3, only a \kcode{depend} clause is present on the \kcode{target_data} construct. 
In Case 3E, identical dependence will appear on all three constituent tasks of the \kcode{target_data} 
construct.
Note that the \kcode{depend} clause on the \kcode{target} construct is superfluous 
due to the implied \kcode{taskgroup} inside the constituent \kcode{task}. Case 4 shows 
how finer control can be achieved through the use of the \kcode{nogroup} clause.

In Case 4, the \kcode{nogroup}, \kcode{nowait} and \kcode{depend} clauses are present on 
the \kcode{target_data} construct. 
In Case 4E, the effect of the \kcode{nogroup} clause eliminates the \kcode{taskgroup} around 
the \kcode{target} region. 
The \kcode{nowait} and \kcode{depend} clauses are applied to the constituent directives that 
accept them.
